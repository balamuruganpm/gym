Product concept: An easy-to-use gym management system for gym owners and staff to manage members, memberships, payments, renewals, and reports from a single application.

Initial business model: Free to use during the first release. No payment gateway or paid external API required for the core product.

## 1. The problem we're solving

Gym owners often maintain member details in spreadsheets, payment records in notebooks, and renewal reminders in WhatsApp. That makes it difficult to answer basic questions quickly:

- Who is currently an active member?
- Who has an overdue payment?
- Which memberships expire in the next seven days?
- How much money was collected today or this month?
- Which members have renewed, and what is their payment history?

GymFlow should answer these questions without requiring the owner to learn complicated software.

### Product promise

> Run your gym's daily membership and payment operations from one simple dashboard, with accurate records and no unnecessary complexity.

01\. Dashboard

- Outstanding payment balances.
- Memberships expiring in 7 and 30 days.
- Recent payments and quick actions.

02\. Member management

- Unique member ID generated automatically.

03\. Membership plans and renewals

- Track start date, expiry date, discount, and final price.

04\. Payments and billing

- Record cash, UPI, bank transfer, and card payments made outside the application.
- Support full and partial payments.
- Calculate the remaining balance automatically.

06\. Reminders and reports

- In-app lists for upcoming expiries and pending dues.
- WhatsApp reminder links with editable, prefilled messages.
- Daily, weekly, and monthly collection reports.
- Outstanding dues report.
- Membership renewal report.
- Export filtered reports.

## 4. MySQL database design

Use a relational database with foreign keys, indexes, appropriate decimal types, and transactions for financial operations.

## Core database tables

gyms

Gym name, contact details, timezone, settings

users

Login email, password hash, name, account status

gym_users

Gym membership, user role, access permissions

members

Member ID, contact details, status, gym ID

membership_plans

Plan name, duration, price, gym ID

memberships

Member, plan, start/expiry dates, agreed price, discount

payments

Membership, amount, method, date, receipt, status

payment_reversals

Reversal amount, reason, original payment, actor

audit_logs

User, action, record type, record ID, timestamp

import_jobs

Upload metadata, counts, result, initiating user

### Important database relationships

- One gym has many users, members, and membership plans.
- One member can have many memberships over time.
- One membership can have multiple payment records.
- Every gym-owned record must have a `gym_id` or be linked through a parent record whose gym ownership is verified.
- Foreign keys should prevent accidental orphaned records.

### Essential financial rules

1. Store monetary values using `DECIMAL(12,2)`, never floating-point types.
2. Calculate balance as agreed membership price minus valid payments and applicable adjustments.
3. Never count voided or reversed payments as collected revenue.
4. Use database transactions when recording payments and reversals.
5. Preserve old membership prices when a plan's price changes.
6. Make payment and receipt identifiers unique within the appropriate scope.

Membership status should be derived from membership dates and applicable business rules, rather than a manually editable label that can become inconsistent.

# Project Specification: GymFlow — Gym Management System

## 1. Project Overview

Build GymFlow, a complete, responsive, production-minded gym management web application using PHP 8.3+, MySQL 8+, HTML5, CSS3, JavaScript, and Bootstrap 5.

The application helps gym owners manage members, membership plans, renewals, payments, outstanding dues, imports, and reports in one dashboard.

The initial release is free to use. Do not integrate a payment gateway or require paid APIs.

This must be a functional application connected to a real MySQL database. Do not build only a UI prototype or use mock data as the main data source.

## 2. Development Rules

- Inspect the existing project workspace before creating files.
- If the workspace is empty, initialize the project cleanly.
- Use maintainable PHP MVC-style architecture with controllers, models, services, middleware, views, and routing.
- Use PDO with prepared statements for database access.
- Use Composer for dependency management.
- Use database migrations and seeders.
- Use environment variables for database credentials and secrets.
- Do not hardcode credentials.
- Use reusable layouts, components, validation, and error handling.
- Keep controllers thin and put business logic in services.
- Do not use a large single PHP file containing the entire application.
- Implement one module at a time and verify it before moving on.
- Do not leave buttons or forms nonfunctional.
- Never report a feature as complete unless it has been implemented and tested.

## 3. Technology Stack

Backend: PHP 8.3+.\
Database: MySQL 8+ with InnoDB.\
Frontend: HTML5, CSS3, Bootstrap 5, vanilla JavaScript.\
Database access: PDO.\
Authentication: PHP sessions and password_hash/password_verify.\
Spreadsheet import: PhpSpreadsheet through Composer, supporting CSV and XLSX.\
Charts: Chart.js.\
Icons: Bootstrap Icons.\
PDF receipts: A maintained PHP PDF library if needed.\
Testing: PHPUnit and appropriate integration tests.

Use Composer-compatible, maintained dependency versions and document the requirements.

## 4. Design Requirements

Create a clean, professional gym management dashboard.

- Responsive sidebar on desktop and accessible navigation on mobile.
- Neutral light theme with restrained accent colors.
- Clear typography, consistent spacing, and accessible contrast.
- Dashboard KPI cards, compact tables, useful filters, and readable empty states.
- Forms with inline validation and helpful error messages.
- Confirmation dialogs for destructive or financial actions.
- Loading states, success notifications, error notifications, and pagination.
- Mobile-friendly tables or alternative layouts.
- Avoid excessive gradients, unnecessary animations, and decorative cards.
- Use realistic seeded demo data only in development.

## 5. Authentication and Multi-Tenant Security

Implement:

- Gym registration and owner account creation.
- Login and logout.
- Secure session handling and session ID regeneration after login.
- Password hashing using PHP password_hash.
- Password reset only if a secure flow can be implemented correctly.
- Owner and staff roles.
- Gym-specific data isolation.
- Server-side role and ownership checks on every protected operation.
- CSRF tokens on state-changing requests.
- Output escaping to prevent XSS.
- PDO prepared statements to prevent SQL injection.
- Login throttling and safe error messages.
- Secure cookie settings and session expiration.
- Audit logging for sensitive operations.

Every business record must be associated with a gym or an ownership-verified parent record. Never trust a gym ID supplied by the browser without checking the authenticated user's access.

Protect private uploads, exports, logs, environment files, and configuration from direct public access.

## 6. Dashboard Module

Display:

- Total members.
- Active memberships.
- Upcoming expiries.
- Expired memberships.
- Outstanding dues.
- Collections today.
- Collections this month.
- Recent payments.
- Renewal reminders.
- Collection chart with date filters.

All metrics must be calculated from actual database records. Define how date ranges, reversed payments, inactive members, and renewals affect the totals.

## 7. Member Management Module

Implement:

- Create, read, update, search, filter, and archive members.
- Generate a unique member number per gym.
- Store name and phone as required fields, with optional email, address, emergency contact, and profile photo.
- Validate fields on both client and server.
- Support pagination and useful empty states.
- Provide a member detail page with membership and payment history.
- Prevent accidental duplicate records where possible.
- Preserve financial history when a member is archived.

## 8. Membership Plans and Memberships

Membership plans must support:

- Plan name.
- Duration in days or months.
- Price.
- Description.
- Active/inactive availability.

Membership records must support:

- Member and plan association.
- Start date and expiry date.
- Original plan price snapshot.
- Discount and agreed price.
- Membership status.
- Renewal history.

Allow custom start dates and expiry dates. Preserve past membership records when renewing. Define date calculations consistently and document the policy for expired memberships, early renewals, and overlapping memberships.

## 9. Payments and Financial Records

Support:

- Cash.
- UPI.
- Bank transfer.
- Card payments recorded externally.

The application records payments; it does not process money.

Allow full and partial payments. Each payment should have an amount, date, method, receipt number, optional reference, status, membership association, and the authenticated user who recorded it.

Requirements:

- Use DECIMAL monetary fields.
- Calculate outstanding balances using valid payment records.
- Use database transactions for payment creation and reversal.
- Never silently delete a payment.
- Implement authorized void/reversal operations with a reason and audit trail.
- Prevent duplicate submissions where possible.
- Generate printable receipts.
- Allow filtering by date, member, method, and status.

Define dashboard collections as actual valid payments received in the selected period, not the total value of membership contracts.

## 10. Membership Renewal and Due Tracking

Provide separate views for:

- Expiring within seven days.
- Expiring within thirty days.
- Already expired.
- Outstanding balances.

Make the expiry window configurable.

Allow authorized users to renew a membership, record a payment, and view previous memberships.

Provide a WhatsApp click-to-chat link with an editable, prefilled reminder. Do not claim that messages were delivered.

Do not implement paid messaging integrations or automatic message delivery in this release.

## 11. Excel and CSV Import/Export

Implement member import using CSV and XLSX.

Workflow:

1. Download a sample template.
2. Upload a file.
3. Validate file type and size.
4. Parse and preview the rows.
5. Validate required fields, dates, and phone values.
6. Detect duplicates.
7. Show row-level errors.
8. Require explicit confirmation.
9. Import valid rows safely.
10. Display an import summary and downloadable error report.

Use safe storage outside the public web root, strict file validation, size limits, and cleanup of temporary files.

Do not trust formulas, macros, file extensions, or MIME types. Do not automatically execute spreadsheet formulas.

Support exporting authorized member and payment reports.

## 12. Reports

Implement:

- Daily collections.
- Monthly collections.
- Payment history.
- Outstanding dues.
- Upcoming renewals.
- Expired memberships.
- Membership plan distribution.

Provide date filters, pagination where appropriate, and CSV exports.

Ensure reports respect gym ownership and payment reversal rules.

## 13. MySQL Database Design

Create migrations and foreign keys for at least:

- gyms
- users
- gym_users
- members
- membership_plans
- memberships
- payments
- payment_reversals
- audit_logs
- import_jobs

Use InnoDB, appropriate indexes, unique constraints, created_at and updated_at timestamps, and consistent naming.

Every gym-owned record must have reliable tenant ownership. Include gym ownership checks in all relevant queries and service operations.

Use DECIMAL(12,2) for monetary values.

Use transactions for multi-step financial operations. Prevent duplicate member IDs and receipt numbers within the correct scope.

Add database migrations and a development seeder. Do not seed demo data in production automatically.
